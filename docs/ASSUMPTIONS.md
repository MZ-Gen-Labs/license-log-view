# 仮想ログ生成の仮定条件

この文書は合成データの仕様です。Siemensが実際に出力したログではありません。ユーザーから指定された条件と、生成のために追加した仮定を分けて記載します。

## 指定条件

|項目|値|
|---|---|
|期間|2026年7月1日〜9月30日、3か月（開始月は生成側の選択）|
|利用者|50人、user01〜user50、PC-01〜PC-50|
|SMD3|10ライセンス、NXとSolid Edgeで共有|
|Solid Edge消費|1起動あたりSMD3の1/3、単独なら30同時起動|
|NX消費|1起動あたりSMD3の1、単独なら10同時起動|
|VBL|Solid Edgeオプション用の独立した200トークンプール|
|主製品|主にSolid Edge、時々NX|
|営業時間|平日9:00〜18:00|
|目標|営業時間の時間加重平均SMD3稼働率80%、ピーク枯渇あり|
|時間外|残業と休日利用あり|

SMD3は整数の「Solid Edge換算単位」30で管理します。SEを1、NXを3単位として、`SE同時数 + 3×NX同時数 ≤ 30` を常に厳守します。SMD3ライセンス単位の消費は `(SE数 + 3×NX数)/3`。SEを30、NXを10、両方を同時に別枠で保有するモデルではありません。

## 追加した業務モデル

- 時刻はAsia/Tokyoの壁時計時刻。タイムゾーン変換は行いません。
- 土日以外を平日とします。日本の祝日・お盆・会社の休日は自動適用しません。`holidays` は初期値が空配列で、設定した日だけ営業日の分母から除外します。
- 平日は8:30〜20:00に取得/返却を発生させます。8:30〜9:00は早出、18:00〜20:00は残業です。18時に一斉終了せず、それ以前のセッションが継続する場合があります。
- 土日は各日35%の確率で利用日となり、10:00〜16:00、少人数の利用を生成します。実際の休日利用日数は乱数で決まります。
- 日々の終了時刻（平日20:00、休日16:00）に残っている取得を全返却します。深夜・日をまたぐ利用はこの通常利用データには生成しません。
- 同一利用者の基本製品は1つだけです。NXとSEの同時起動、多重起動は今回の業務仮定では禁止です。
- 最初の8人はNXも利用し、基本製品の取得機会の20%でNXを選びます。それ以外の機会はSEを選び、残り42人はSEだけを使います。この20%は全員の利用割合ではありません。
- 空いているユーザーを乱数順で選ぶため、利用時間は全員均等ではありません。監査で50人全員に利用実績があることを確認します。
- 基本製品の予定取得時間は60〜180分、5分単位の一様分布。ただし終業時刻により短縮します。
- モデル更新間隔は5分。ログも5分刻みです。精密な時刻分布を持つ実ログを再現したものではありません。解析器は秒単位の時刻から時間積分できます。

### 営業時間の需要曲線

営業時間全体に対する経過比率で次の需要変動を加えます。9時間の勤務なら時刻はおおよその目安です。

|経過比率|おおよその時刻|基準需要からの増減（SE換算単位）|
|---|---|---:|
|0〜9%|9:00〜9:49|-7|
|9〜22%|9:49〜10:59|-2|
|22〜36%|10:59〜12:14|+4|
|36〜46%|12:14〜13:08|+1|
|46〜57%|13:08〜14:08|-5|
|57〜80%|14:08〜16:12|+4|
|80〜93%|16:12〜17:22|0|
|93〜100%|17:22〜18:00|-6|

日ごとに最大±1.5単位、5分ごとに最大±1単位の乱数変動を追加します。基本製品の取得中人数が需要を超えていても、需要曲線に合わせるための強制返却は行いません。

日付の日部分が5の倍数となる営業日の14:00〜14:30には、定期的な集中作業の仮定として、SMD3容量+4単位の需要を発生させます。これは30の容量を超える「要求」であり、成功する取得は30以下です。自然発生するピークと併せて枯渇・再試行を生成します。実際の企業でこの日程があるという主張ではありません。

早出は2〜4単位の需要、残業は18時時点で約8単位から20時に向かって低下する需要、休日は3〜7単位の需要を想定します。既存セッションが残るため、実消費はその需要値を上回ることがあります。

基準需要を16回の二分探索で調整し、実際の取得時間の積分が80%へ近づく候補を選択します。80%は要求量ではなく、成功した取得の消費量です。5分単位・整数取得のため完全な80.000%を強制せず、監査許容差は±0.2パーセントポイントです。

## OUT（取得成功）

1. 基本製品未取得の利用者が、SEまたはNXを要求します。
2. `現在のSMD3消費単位 + 要求単位 ≤ 30` の場合だけ成功。
3. `OUT: "SYNTH_SMD3_SE" userNN@PC-NN` または `SYNTH_SMD3_NX` を出力。
4. セッションごとに一意の `B000001` 等を付け、取得直後から返却時刻まで占有します。

取得要求の優先順位は空いている利用者の乱数順です。NX要求が残量2単位で拒否されても、別のSE要求が残量1単位で成功する可能性があります。これを「満杯でない拒否」と誤解しないよう、要求量と残量を監査します。

### VBLオプションOUT

Solid Edge取得中で、現在オプションを取得していないユーザーごとに、各5分で2.5%の確率でオプションを要求します。1人あたり同時オプションは1つに限定します。4種類を同確率で選択し、予定取得時間は20〜60分、5分刻みの一様分布です。

|合成機能名|想定オプション|仮の消費トークン|
|---|---|---:|
|SYNTH_VBL_SIM|Simulation|40|
|SYNTH_VBL_CAM|CAM|25|
|SYNTH_VBL_MBD|MBD|15|
|SYNTH_VBL_ROUTING|Routing|10|

この消費表はモデリング用に選んだ仮定です。Siemensの正式な製品名・ライセンス機能名・消費値を保証しません。オプション機能のOUT1件に設定トークン数を対応させます。トークン親機能のOUTを重ねて出力しないため、合成データに二重消費はありません。

VBL消費合計が200を超えないときだけOUTを出力し、一意な `V000001` 等のセッションIDを付けます。VBLはSMD3と独立です。VBLの取得は追加でSMD3を消費せず、SMD3が満杯でも、すでにSE取得中ならVBL取得は可能です。平均VBL稼働率の数値はユーザーから指定がないため固定せず、この使用頻度による実績値を記録します。

## IN（返却）

- 予定終了時刻に達した基本製品またはオプションを返却します。
- 基本製品終了時には、その利用者のVBLオプションを先にINし、基本製品をその後INします。VBLだけがSEなしで残ることはありません。
- 一日の最終時刻に残りを全返却します。
- INにはOUTと同じ機能・利用者・端末・セッションIDを付けます。
- 同時刻の処理順は、期限に達した基本製品に付随するオプション返却 → 基本製品返却 → その他の期限オプション返却 → 基本製品取得要求 → オプション取得要求です。
- OUTのないIN、二重IN、返却欠落は今回の通常利用データには生成しません。

## DENIED（取得拒否）

`現在のプール消費 + 要求量 > 保有量` の場合だけ、`Licensed number of users already reached. (-4,342)` を付けてDENIEDを出力します。容量はSMD3が30換算単位、VBLが200トークン。

- DENIEDはライセンスを取得しません。消費量・利用時間を増やさず、対応するINも出しません。
- 拒否されたユーザーは将来の更新時刻に再び要求する可能性があります。拒否イベント数は重複利用者をまとめない再試行込みの件数です。
- 基本製品要求は拒否時に65%の確率でその更新時刻の追加要求ループを終えます。残る35%では別ユーザーの要求を続けます。これは生成処理の仮定で、製品の再試行仕様ではありません。
- VBL拒否後も既存SEセッションは継続します。
- 許可ユーザー制限、期限切れ、機能不一致、通信障害等のその他の拒否理由は生成しません。

## ログ形式と正確性の範囲

```text
00:00:00 (ugslmd) TIMESTAMP 7/1/2026
09:00:00 (ugslmd) OUT: "SYNTH_SMD3_SE" user01@PC-01 [session=B000001]
10:00:00 (ugslmd) IN: "SYNTH_SMD3_SE" user01@PC-01 [session=B000001]
```

FlexNetの基本デバッグログ形式を参考にしています。daemon名ugslmd、SYNTH機能名、sessionタグは合成データの仮定です。sessionタグは取得/返却対応を正確に検証するための拡張で、Siemens実ログで存在することを保証しません。1イベントで1つの基本製品・オプション取得を表現します。月単位でファイルを分け、各日00:00に明示TIMESTAMPを出力します。これは標準の定期TIMESTAMPの間隔を忠実に再現したものではありません。

除外するケース：サーバー再起動、借用(BORROW)、ハートビート喪失、強制返却、ログ欠落、QUEUE、冗長サーバー切替、複数サイト、親子機能の多重記録、バージョン別機能、夜勤、固定長期セッション。これらは実ログ対応の追加検討項目です。解析器の一部異常処理はselftestで別途検証し、通常利用ログに混ぜません。

## 集計式

- 営業時間内SMD3稼働率 = 営業時間内の `(SE数/3 + NX数)` の時間積分 ÷ `(10 × 営業時間数)`。
- 営業時間内VBL稼働率 = 営業時間内の使用トークンの時間積分 ÷ `(200 × 営業時間数)`。
- 営業時間数 = 設定営業日の9時間の合計。土日と設定休日は0時間。
- 24時間平均 = 全期間の消費時間積分 ÷ `(保有量 × カレンダー日数 × 24時間)`。
- 製品利用時間 = 基本製品の取得から返却までの時間。SEは1/3換算前のSE席時間、NXはNX席時間。
- VBL token·h = オプション取得時間 × その消費トークン数。利用h = token·h ÷ 設定トークン数。
- SMD3満杯時間 = 営業時間内に消費量が10に達していた時間。NX要求が残容量不足となる時間と必ずしも一致しません。
- 時間外消費 = 全期間SMD3ライセンス時間 − 営業時間内SMD3ライセンス時間。早出・残業・休日を含みます。
- 取得中 = ライセンスが占有されていた状態であり、CAD操作・CPU稼働・実作業時間を示しません。

5分区間への表示集約も、秒単位のイベント区間と交差する長さを積分します。単純なOUT件数割合や一定間隔の瞬間サンプル平均は稼働率の計算には使用しません。

## 検証データの保存

テキスト出力前のイベントを `truth-events.json` に保存します。監査はテキストを再解析して全イベントを一致比較し、生成側イベントから独立に取得/返却ペアを再構成して機能別unit·hを算出します。解析器の結果と照合し、全時点の容量、拒否時残容量、SE依存、利用者数、平均80%を確認します。

乱数の再現性は同じ.NETバージョン・同じ設定を前提とします。異なる.NETバージョンの乱数実装まで同一であることは保証しません。固定ログのハッシュと監査実績はVALIDATION.mdに記録します。

## 同梱ログの観測実績

平均SMD3 80.1146%、平均VBL 35.7997%（いずれも営業時間）。SMD3拒否114件、VBL拒否41件。休日利用は12日。詳細数値・ハッシュ・監査範囲はVALIDATION.mdを参照。
