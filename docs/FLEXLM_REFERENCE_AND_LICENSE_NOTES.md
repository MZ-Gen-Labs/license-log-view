# FlexLM解析の参考資料とOSS・名称・ライセンス検討メモ

作成日・公開情報の確認日：2026-10-13（Asia/Tokyo）  
対象：`license-log-view`プロジェクト（現在の表示名：License Log View）  
位置付け：仕様調査・独立実装の進め方を整理する検討メモ。正式な製品名称や、このプロジェクト自身の配布ライセンスを決定する文書ではありません。

## 1. 今回の検討の結論

- FlexLM／FlexNet Publisherのログ仕様は、Revenera公式資料を第一の根拠にする。
- OSSの説明・対応ケースは、解析の考え方や検証項目を考える参考になる。ただし、OSSの実装が公式仕様・Siemensの挙動を保証するわけではない。
- 技術的な事実、ログの形式、一般的な解析手順・アルゴリズムを理解し、独立に実装するだけなら、通常、参照先のMIT等の条件を自作ツールに引き継ぐ必要はない。
- コードのコピー・改変・忠実な他言語移植と、文章・図・テストコードの転載は別に扱う。利用する部分について、著作権とライセンス条件を確認する。
- SMD3の共有換算とVBLの消費数は、一般的なFlexLMのログ形式からは決定できない。Siemensの契約情報・実際の機能名・取得構造・実ログで確認する。

## 2. 仕様・解析設計の参考資料

### 2.1 Revenera公式資料：仕様確認の第一候補

[FlexNet Publisher 2026 R1 License Administration Guide](https://docs.revenera.com/fnp/2026r1/pdf/fnp_LicAdmin.pdf)

- 第22章「Debug Log File」：基本の行形式、OUT／IN／DENIED等のメッセージ、TIMESTAMP、verbose形式。
- 第21章「Report Log File」：report logの位置付けと設定。
- `NOLOG`の説明：イベントの出力抑制がある場合の確認。
- 日付付き出力・起動時の日付やタイムゾーン情報：時刻だけの行から日時を復元する際の確認。

デバッグログは状態・エラーメッセージを含むログで、使用状況集計用のreport logとは異なります。デバッグログの取得・返却イベントを集計する場合、出力抑制、途中から始まるログ、ローテーション、欠落、再起動、バージョンやvendor daemonの違いを考慮する必要があります。

公式マニュアルはMIT等のOSSライセンスで公開された文書ではありません。技術的な事実を確認することと、マニュアルの文章・表・図・PDFを自分たちの配布物へ転載することは区別します。転載・再配布は文書の権利表示と利用条件を確認してください。今回のメモにはPDFを同梱せず、参照リンクを記載しています。

### 2.2 goflexlm：ログ解析器の対応ケースの参考

[danofsteel32/goflexlm](https://github.com/danofsteel32/goflexlm)

公開READMEでは、Go製のログ解析ライブラリとJSON Lines出力コマンドとして、次の対応を説明しています。

- 通常形式と日付付き形式のログ。
- コンパクト形式とverbose形式のOUT／IN／DENIED／QUEUED／DEQUEUED。
- 日付・UTCオフセットを得た後の日時復元と日付またぎ。
- 数量や管理操作による返却理由の保持。
- 不正な行の診断を残し、以後の解析を継続する設計。

MITライセンスの公開表示を確認しました。今回はコードを取り込むためではなく、対応形式と異常系の検証項目を洗い出す参考資料として挙げています。実装・品質・Siemens実ログとの互換性は、この調査では検証していません。

### 2.3 ghostseat：セッション復元と診断設計の参考

[vanshdev0101/ghostseat](https://github.com/vanshdev0101/ghostseat)

READMEには、ログの解析 → OUT／INに基づくセッション復元 → 検出・診断 → レポートという設計が説明されています。未返却、拒否、同時取得、途中から始まるログ等をどう扱うかの参考になります。

拒否原因や未返却理由は、ログだけで確定できない場合があります。他ツールの診断名を、そのまま事実として採用しないようにします。このメモではghostseatの商用利用可否・ライセンスを確定していません。将来コードを利用する場合は、対象版のLICENSEと依存物を改めて確認します。

## 3. 自分たちの解析仕様に落とし込む項目

以下は設計・検証項目であり、現在のツールがすべて実装済みという意味ではありません。

|項目|仕様として決める内容|
|---|---|
|日時復元|明示日付、TIMESTAMP、タイムゾーン、深夜の日付またぎ、日付不明時の扱い|
|イベント解釈|取得・返却・拒否・キュー・管理操作・起動停止を区別する|
|取得／返却対応|機能・利用者・端末・ID・数量による対応付けと、IDがない場合の曖昧さ|
|同時使用量|取得で加算、返却で減算。拒否は消費量を増加させない|
|数量|複数取得、部分返却、重複グループ等をどう扱うか|
|異常系|対応OUTのないIN、未返却、未知機能、未対応形式、容量超過を警告する|
|再起動・ログ欠落|占有が続いたか解除されたかを推測で確定せず、不確実性を記録する|
|複数ファイル|ローテーション、期間またぎ、重複区間、複数サーバーの混入を扱う|
|時間積分|イベント間の占有量×経過時間から利用量を算出する|
|営業時間|平日9〜18時の分母と、早出・残業・休日・24時間全体を区別する|
|SMD3|指定モデルではSE数＋3×NX数を30換算単位の共通プールで管理する|
|VBL|機能ごとの消費数、親子機能の二重記録、SE取得への依存を実データで確認する|

現在の合成ログには、取得／返却対応を明確にするため、独自の`[session=ID]`タグを付けています。このタグがSiemens実ログに存在することは保証していません。実ログでIDが得られない場合、同一機能・利用者・端末の複数取得を一意に復元できないことがあります。

今回の機能名とVBL消費数は合成モデル用の仮定です。実ログへの適用は、既存の[ASSUMPTIONS.md](ASSUMPTIONS.md)、[VALIDATION.md](VALIDATION.md)、実ログの確認結果と併せて判断してください。

## 4. 仕様・ロジックを参考にした場合のライセンス条件

### 4.1 一般的な考え方

日本の著作権法第10条第3項は、プログラムの著作物の保護が、作成に用いるプログラム言語・規約・解法には及ばないとしています。具体的なコードや文章の創作的表現と、その背後にある手順・考え方を区別します。

- [著作権法第10条（e-Gov、参照表示版は2023-11-02）](https://laws.e-gov.go.jp/law/345AC0000000048?occasion_date=20231102)
- [米国著作権局：What Does Copyright Protect?](https://www.copyright.gov/help/faq/faq-protect.html)

この整理は一般論です。具体的な実装が他者の表現を複製・翻案しているか、契約条件が適用されるかは個別の事情で判断が変わります。参照した法令の表示版・契約・対象地域も、正式な配布判断時に確認します。

|参照・利用方法|通常の扱い・注意点|
|---|---|
|ログ形式・イベントの意味を理解し、自分で実装する|通常、参照先OSSのライセンス条件を自作ツールへ引き継ぐ必要はない|
|OUTで加算、INで減算、時間積分などの一般的手順を参考にする|通常、同様。具体的なコード表現の流用とは区別する|
|コードをコピー・改変する|利用する部分について元のライセンス条件に従う|
|既存コードを忠実にC#へ翻訳する|コピー・翻案に当たる可能性があり、言語を変えただけで独立実装とはいえない|
|READMEの文章・図・テストコード等を転載する|対象の著作権・ライセンス条件を確認する。参照だけと複製を区別する|

コードを読んだという事実だけで、自動的に自作ツール全体がMITになるわけではありません。一方、「コピー＆ペーストしなかった」「変数名を変えた」だけでは、独立実装の根拠として十分とは限りません。具体的な表現・構造の引き継ぎがある場合は、利用した部分を特定して条件を確認します。

### 4.2 MITコードを実際に利用する場合

[MITライセンス本文（Open Source Initiative）](https://opensource.org/license/mit)

MITは改変・商用利用・配布等を認め、ソフトウェアの複製物または実質的部分に著作権表示と許諾文を含めることを条件とします。MITコードを取り込んでも、自作ツール全体をMITとして公開する義務や、通常のソース公開義務が発生するわけではありません。取り込んだ部分の表示・許諾文は維持します。

公開リポジトリにコードが見えることだけで、自由に利用できるとは判断しません。対象版のLICENSE、ファイルごとの表示、第三者素材・依存物の条件を確認します。

### 4.3 Apache-2.0とGPL-2.0

- [Apache License 2.0本文](https://www.apache.org/licenses/LICENSE-2.0)：商用利用・改変・配布が可能。配布時のライセンス文、関連する権利表示、変更したファイルの変更表示、該当するNOTICEの扱い等を確認します。
- [GPL-2.0の条件整理](https://choosealicense.com/licenses/gpl-2.0/)：商用利用自体は禁止されません。GPL対象物やその派生物を顧客へ配布する場合、GPLに従った配布・対応ソースの提供等が必要です。社内利用、改変物の配布、別プログラムとの組み合わせは区別して確認します。

著作権・OSSライセンスとは別に、特許、NDA、資料の閲覧条件、ソフトウェアの契約上の制限が問題となる場合があります。OSSの名称を使う権利・商標上の扱いも、コード利用許諾とは別です。

## 7. このプロジェクトでの参照・実装記録の残し方

1. 公式資料と利用許可のある実ログから、必要なログ形式・意味・例外条件を抽出する。
2. 技術的な事実と、自分たちの推定・業務仮定を分け、自分たちの言葉で解析仕様を書く。
3. OSS資料は対応ケースの確認に用い、独自のC#実装と合成テストデータを作る。
4. 参照URL、確認日、使用した仕様の範囲、対象版を記録する。参照先を記すことは設計根拠の追跡のためで、参照だけの場合にMIT表示義務が発生するという意味ではない。
5. 将来、コード・図・文章・テスト等を取り込む場合は、参照資料の一覧と別に、取り込んだファイル・箇所・版・ライセンス・変更内容を記録する。
6. 顧客配布前に、取り込み記録と必要なLICENSE／NOTICE／著作権表示等を確認する。

本メモは過去の実装全体に第三者コードの流用がないことを監査・証明するものではありません。また、参照したOSSのコード・マニュアルPDFは今回の文書保存では取り込んでいません。
